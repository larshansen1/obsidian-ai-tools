Problem. cli.py is a 2,371-line shallow module — its interface (17 CLI commands) is nearly as wide as its implementation, which mixes progress callbacks, error formatting, typer table rendering, and business logic in the same functions.

Solution. Introduce a commands/ package where each file handles one command group, plus a DisplayHandler that owns all typer output — cli.py becomes a router under 200 lines.

Wins

  • → locality: adding a command touches one file, not the monolith
  • → interface shrinks: each command module exposes one function
  • → leverage: DisplayHandler reused across all 17 commands
  • → seam exposed: display logic becomes independently testable

Decouple vault access and observability from note generation

Strong in-process

llm.py (278 lines)

Before — generate_note() does everything

build_prompt() — loads template + injects metadata
← build_index() import [VAULT LEAK]
← top tags discovery from vault [VAULT LEAK]
openrouter POST → parse_llm_response()
← ObservabilityDB() [COST RECORDING LEAK]
return Note

After — generate_note() is pure

ingestion.py orchestrates:

existing_tags = get_top_tags(vault)

note = generate_note(content, existing_tags)

record_cost(cost_info)

llm.generate_note(content, existing_tags)

→ (Note, CostInfo) [pure, no side-effects]

Problem. generate_note() leaks across two seams: it imports the vault indexer to discover existing tags, and it directly instantiates ObservabilityDB to record cost — making it untestable without a real vault and a real database.

Solution. generate_note() accepts existing_tags as a parameter and returns a (Note, CostInfo) tuple; the caller (ingestion.py) passes in tags and records cost.

Wins

  • → seam is clean: llm.py has zero I/O — no vault, no DB
  • → interface shrinks: tests pass tags directly, no vault fixture needed
  • → locality: cost recording lives in one place (ingestion.py)
  • → leverage: generate_note() becomes reusable outside the ingestion flow

Problem. WebProvider and PDFProvider each declare a private _limiter = RateLimiter(delay=2.0) global and implement the same primary→fallback cascade pattern independently — two shallow implementations of the same idea.

Solution. Extract a FallbackChain base helper (not a new module seam — private to the providers package) and share a single RateLimiter instance.

Wins

  • → locality: fallback logic changes in one place
  • → interface shrinks: new provider needs no fallback boilerplate
  • → rate-limit correctness: two global limiters can interleave — one shared instance prevents that

Problem. ObservabilityDB is instantiated at four call sites (llm.py + three in cli.py), each opening its own DuckDB connection — four shallow entry points where one deep module with a get_db() accessor would do.

Solution. observability.py exposes a lazy singleton get_db() → ObservabilityDB; callers drop their constructor calls.

Wins

  • → locality: DB path logic lives once
  • → depth increases: callers know nothing about the DB path or connection lifecycle
  • → interface shrinks: tests swap the singleton once, not four times
  • → leverage: connection pooling or migration added once, paid back everywhere

Top recommendation

Start with Candidate 2 — decouple llm.py

It's the smallest change with the highest payoff: one function signature edit (add existing_tags param, return (Note, CostInfo)) eliminates two hidden seam crossings — the vault import and the ObservabilityDB instantiation. The module becomes purely testable with no fixtures. It also naturally feeds Candidate 5 (ObservabilityDB singleton), since cost recording moves to ingestion.py where the singleton belongs. After that, Candidate 4 (delete api_contracts.py) is a five-minute cleanup that eliminates dead maintenance surface. Candidate 1 (cli.py decomposition) is the highest-leverage long-term move but also the most disruptive — do it after the smaller seams are clean.
